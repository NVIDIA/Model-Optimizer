Reproducibility notes#

These notes describe how the checkpoints were prepared and evaluated for the evaluation guidelines.

Baseline and Candidate checkpoints#

Baseline is NVFP4 Qwen3.6-35B-A3B after PTQ and QAD. The PTQ/QAD tutorial describes that recipe.

Candidate was trained directly from Baseline using KTO in NeMo RL, with an unchanged copy of Baseline as the reference model. We identified 55 SciCode subtasks on which Baseline had shown reasoning loops: 44 supplied training examples and 11 were reserved for evaluation. Training used model-generated responses: 104 correct and 104 containing reasoning loops. After 13 optimizer steps (KTO beta 0.05, learning rate 1e-6) with simulated NVFP4 quantization, Candidate was exported to NVFP4.

The evaluated checkpoints and paired measurements are available in the evaluation collection. It also links to the analysis record, pinned to a fixed commit, with selected question/subtask IDs, evaluation settings, analysis scripts and seeds. Both sources require NVIDIA internal access.

Data preparation#

For representative evaluation, select seeded random subsets before inspecting results, stratifying by subject where appropriate. Freeze matching question IDs across models.

  • MMLU-Pro: we sample 1,000 of 12,032 test questions across all 14 subjects, in proportion to each subject’s size.

  • SciCode: the main results cover 294 of 338 subtasks, excluding the 44 used for KTO recovery training. KTO used model-generated responses, not reference answers.

  • Focused SciCode: we use 11 held-out subtasks where Baseline previously showed reasoning loops to check whether Candidate reduces those loops.

Baseline and Candidate answered the same benchmark questions with matched generation seeds.

Evaluation setup#

For benchmark evaluation, both models generated responses with temperature 0.6, top-p 0.95, a 131072-token completion cap, and a 262144-token context window.

For AA-Omniscience, the Codex assistant graded each response using the reference answer, without being told whether Baseline or Candidate produced it. The reported grading model was GPT-6.1 Sol with xhigh reasoning effort. Deliberate abstention means choosing not to answer; empty answers and uncertain guesses do not count.

Saved metrics#

We save the means, observed standard deviations, confidence intervals, and p-values shown in the guide’s four plots as CSV summaries:

  • MMLU-Pro and SciCode: Candidate accuracy at fixed response budgets — data used in the guide section Choose between question-level and repetition-level analysis. CSV file: budget-allocation-accuracy.csv.

  • MMLU-Pro and SciCode: accuracy and cap-hit-rate differences at fixed response budgets — data used in the same section. CSV file: budget-allocation-differences.csv.

  • SciCode: cap-hit rates — data used in the guide section Collect as much evaluation data as you need. CSV file: scicode-cap-data-volume.csv.

  • MMLU-Pro: accuracy regression — data used in the guide section Collect as much evaluation data as you need. CSV file: mmlu-accuracy-data-volume.csv.

Statistical methods#

For accuracy, cap-hit and missing-final-answer rates, and mean completion length, we calculate the difference by subtracting Baseline’s value from Candidate’s. Accuracy and rate changes are in percentage points; length differences are in tokens, including reasoning tokens.

  • Accuracy and mean completion length: average each model’s repetitions within each question, then subtract Baseline’s average from Candidate’s for that question. Across these paired question differences, use a two-sided t-based 95% confidence interval and one-sided paired t-tests for the stated direction. Degrees of freedom equal the number of questions minus one. Median lengths describe all individual responses; the length tests concern means.

  • Non-inferiority: test whether Candidate’s accuracy loss is smaller than an acceptable margin. For differences in pp, the t statistic is (mean_difference + margin) / standard_error, using the upper tail and the same degrees of freedom. The guide examines margins of 2, 1, 0.5, and 0.1 pp.

  • Failure, abstention, and incorrect-answer rates: calculate paired-bootstrap 95% confidence intervals by sampling questions with replacement, keeping each question’s repetitions and both models together. MMLU-Pro and SciCode use 100,000 resamples; AA uses 50,000, preserving 100 questions per domain. The interval endpoints are the 2.5th and 97.5th percentiles.

The question-level tests treat questions and SciCode subtasks as independent. Related subtasks from the same parent problem may need to be analyzed together.

Each test uses p < 0.05. We do not make that threshold stricter because other metrics were also tested. Reverse-direction p-values provide context only.

Observed variation at fixed response budgets#

For a budget of B responses per model and R repetitions, each score averages B/R questions with R repetitions each. We split the saved question order into consecutive groups of B/R questions and the repetition order into blocks of R. Each response appears once per allocation; both models use matching groups. This gives 20 group scores for each allocation, without random resampling.

The pools contain 1,000 MMLU-Pro questions × 20 repetitions and the first 280 subtasks in the frozen SciCode evaluation order × 20 repetitions. Using 280 of the 294 held-out subtasks allows exact grouping at every tested repetition count; the main SciCode tables still use all 294. The dotted references use all 1,000 MMLU-Pro questions or 294 SciCode subtasks, each with 20 repetitions.

We report the mean and sample SD across the 20 group scores, using a divisor of 19 for the variance. Accuracy means are percentages; Candidate minus Baseline differences and all SDs are in percentage points. The means stay fixed because every allocation partitions the same saved response pool. Groups can share question or repetition IDs, so their observed spread is descriptive; these are not 20 new independent benchmark runs or a validation of confidence-interval coverage.

Question-level and repetition-level p-values#

For the SciCode benchmark, a response scores 1 if it hits the completion cap and 0 otherwise. Both methods test whether Candidate has a lower cap-hit rate, using identical responses from 294 subtasks at each repetition count.

Question-level: average each model’s cap-hit outcomes across repetitions within each subtask, then subtract Baseline’s average from Candidate’s. This gives 294 paired differences. To calculate the exact paired permutation p-value, swap the models’ results within each subtask or leave them unchanged, keeping all repetitions together. The p-value is the fraction of possible swaps giving a mean difference equal to or lower than the observed difference, including ties.

Cap hits are rare, so most subtask differences are zero. The permutation test avoids relying on a t-distribution approximation for these sparse differences. It assumes that the models’ results within each subtask are interchangeable under the null hypothesis.

The outcomes are binary, but a simple binomial test on pooled responses would ignore question pairing and repetitions within each question. With one response per model and question, an exact McNemar test is another paired option.

We use the same paired permutation method for the guide’s cap-hit, missing-final-answer, abstention, and incorrect-answer p-values, taking the tail in the stated direction.

Repetition-level: for each model and repetition, divide the number of cap hits by 294. Apply a one-sided Welch t-test to the two lists of repetition rates, testing whether Candidate’s mean is lower than Baseline’s. The calculation uses each model’s sample variance across repetitions and Welch’s degrees of freedom. It treats runs as independent and allows different variances for the two models. At least two repetitions per model are needed to estimate those variances; with very few repetitions, the estimates may be unstable.

Reproducibility limits#

The checkpoints and paired measurements are stored outside the public ModelOpt repository. To keep the repository lightweight, we include summary results here rather than question-level data, generated responses, or a full experiment environment, consistent with the Qwen3.6 PTQ/QAD tutorial.
